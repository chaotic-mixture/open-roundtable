# v0.0.6 acceptance results and reproduction

[中文验收记录](#v006-验收与复现)

Two processes on one machine discovered each other through a shared public directory. Node A sent a synthetic scheduling request. Node B ran the expert and local model, recorded their decision and charges, then stopped before A received its receipt. A retried the same request after B restarted with its original database.

| What was checked | Observed with `qwen3.5:9b` |
| --- | --- |
| Delivery | B received two copies of the request. A received one result and the topic reached `RESOLVED`. |
| Work and accounting | One expert call and one model call. Both ledgers recorded the same charge of 2 test credits. The kernel balance reached zero. |
| Model usage | 290 input tokens and 7 output tokens in the reference run. |
| Private data | Markers inserted into each private database had zero matches in the public directory, recorded transmissions and expert and model call records. |

To reproduce the tagged release, run these commands from its source root with Python 3.11 or later. The first command uses a model substitute for the retry regression. The second needs a running local Ollama service with the named model and a fresh output directory. The last command checks the saved evidence offline.

```sh
python tests/verify_core.py
python -m examples.two_node_demo run reports/release-peer-run --model qwen3.5:9b
python -m examples.two_node_demo verify reports/release-peer-run
```

The release exercised a lost receipt **after** B committed the result. An interruption during inference, before a receipt exists, still requires reconciliation. The processes used separate ports and databases on loopback with a trusted directory. Cross-host authentication and encryption were outside this release test. The privacy check covered the recorded surfaces listed above. Full-machine network capture was outside its scope.

## v0.0.6 验收与复现

A 和 B 从同一个公开目录读到节点描述，并各自保存对方地址。A 发送合成排班议题，B 的专家生成并核验候选，本机模型选择方案，双方表决。故障注入点在 B 已保存结果和费用、A 尚未收到回执时。B 退出后以新进程打开原库，A 重发同一个议题。

| 检查项 | 参考实测（qwen3.5:9b） |
|---|---|
| 接收与回传 | B 收到两次相同请求，A 收到一次结果，议题 RESOLVED |
| 调用与扣费 | 专家一次、模型一次。两端记录同一笔 2 个测试 credits，内核余额为零 |
| 模型回执 | 输入 290 tokens，输出 7 tokens；可随模型版本变化 |
| 私有数据 | 两端私库各植入随机来源和正文标记，公开目录、记录的传输、专家及模型调用记录中均为零命中 |

## 复现

在源码根目录使用 Python 3.11 或更高版本。第一条命令运行完整回归、合成演示和 SQLite 独立回读；双节点回归用可计数的本机模型替身验证重发次数，也检查篡改费用和植入泄露标记时验收会失败。真实会诊另需 Ollama 已运行并已安装指定模型。run 的目标目录必须尚不存在，verify 可在模型和两节点退出后运行。

~~~
python tests/verify_core.py
python -m examples.two_node_demo run reports/release-peer-run --model qwen3.5:9b
python -m examples.two_node_demo verify reports/release-peer-run
~~~

## 本版一并发布

- 排班会诊接受自定义输入和验收条件，记录候选、提案版本和对应表决，支持扩展候选与独立复核。

- 公开库按记录设置共享；私有库支持封闭、本机维护和经授权的 API 维护。双节点演练只传递已公开的合成议题。

## 验证边界

两个节点各有独立进程、端口和数据库，共用一台机器、回环网络和可信目录。此次覆盖接收方提交成功后丢失回执的窗口。推理已开始且尚无持久回执时，执行状态需另行核对。跨机器部署、身份认证、加密传输及任意故障下的恰好一次执行仍待验证。隐私结论限于演练植入的标记和实际检查的记录，未做全机抓包。credits 是项目内部测试单位。公开版本仅提供 Git 源码，原始账本与传输记录留在本地。
